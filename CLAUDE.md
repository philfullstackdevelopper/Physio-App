# EasyPhysio — Project Specification

This file is the source of truth for this project. Read it fully before making changes. If a request conflicts with this spec, flag the conflict instead of silently deviating. If you notice the *code* has drifted from what this file says, flag that too and propose a correction to this file rather than silently trusting either one — this file has gone stale before and caused an agent to treat live features as forbidden.

## 1. What this app is

A multi-tenant SaaS platform ("suivi en ligne") for physiotherapy instructors (kinés) to manage patient exercise programs and track adherence. One platform, many instructors, each instructor's patients and data completely isolated from every other instructor's.

The default interface language is French. **Since 2026-11-06 (Philippe) the app is bilingual French / English, and built to take more languages later**: every user picks a language at signup (FR · EN switch on the home page / signup) and can change it anytime (patient: `/patient/compte`; kiné: `/dashboard/informations`). UI strings live in `messages/<locale>/<area>.json`, read through **next-intl** (`i18n/request.ts`). There is no locale in URLs: the choice is stored in `app_users.locale` and mirrored in the `NEXT_LOCALE` cookie. Never hard-code new UI text in a component — add it to both `messages/fr/…` and `messages/en/…`. Platform content stored in the database (exercise instructions, condition and séance names/descriptions, body areas) is translated by `lib/i18n/dbContent.ts`: a dictionary `i18n/content/en.json` keyed by the exact French text, applied to every read (GET) through the Supabase clients (`global.fetch` in `lib/supabase/{server,client}.ts`); a French text with no exact match (new or edited) simply shows in French, and kiné-written text is never touched. Exercise names are already English in the database and are not in the dictionary. When a migration adds or rewrites platform text, add its English to `i18n/content/en.json`. Legal texts (CGU, privacy, legal notice, health-data consent), billing wording (« hors nomenclature », art. R.4321-98 CSP) and clinical content (exercise names/instructions, condition names) are translated by Claude as **drafts flagged as needing human review** (lawyer / partner kiné) — never treat those English versions as validated. Going abroad (Philippe, 2026-10-13) still also means per-country settings later (Belgium, Switzerland, Luxembourg, Quebec: currency / legal texts / invoice wording) — not started; keep France-specific things (RPPS check, euro amounts, legal wording, « hors nomenclature » invoice text) in the places they already live (`lib/billing/*`, the signup/approval code) rather than scattering new copies across screens.

## 2. User roles

There are three roles. Build for exactly these three — do not add extra roles (e.g. "clinic admin," "assistant") unless explicitly asked.

**Admin** (the platform owner, i.e. Philippe): manages the platform itself. Built so far: approving new instructor signups from `/admin` (see migration `0023_instructor_approval.sql` — instructors default to `pending` on self-serve signup and must be approved before they can use the dashboard). Also in `/admin`: the overview/suspension of all kinés, **test accounts** (fake kiné + fake patients created in one click, migration `0064`), and the **launch waiting list** (migration `0066`): visitors leave their e-mail on the home page (`components/WaitlistForm.tsx`, block `#liste-attente`), stored in `internal.waitlist` (server-only, never exposed by PostgREST); `/admin` lists them with a « copier les adresses » button. No automatic e-mail is sent — Philippe writes to the list himself. **Kiné signups OPEN since 2026-11-01 (Philippe): `SIGNUPS_OPEN = true`; patient invitations stay closed (`PATIENT_INVITATIONS_OPEN = false`) until the HDS region move and Stripe live mode — no real patient health data on the non-HDS host. A new kiné is approved automatically (since 2026-11-02); nothing blocks an approved kiné who hasn't paid (Stripe is still in test mode, so it's a free trial in practice).** Previous state: **Pre-launch lock (2026-10-12, `lib/launchFlags.ts`)**: `SIGNUPS_OPEN = false` and `PATIENT_INVITATIONS_OPEN = false`. While they are false, nobody can create an account (`/signup*` show « les inscriptions ouvriront au lancement » with the waiting-list form, `/signup/finalize` creates no instructor row, every « Créer un compte » button on the home page points to the waiting list) and no kiné can invite a real patient (`addPatient` / `reactivatePatient` refuse, except for the admin). Existing accounts — Philippe's and the admin-created test accounts — log in normally; testers discover the product through test accounts. At launch, set both to `true`.

**Instructor** (the physiotherapist / kiné): signs up, waits for admin approval, logs in, manages their own roster of patients, builds programs for patients from a shared exercise library, views patient adherence, messages their patients, and connects Stripe to get paid.

**Patient**: logs in, accepts CGU + health-data consent, sees their assigned program for today, marks exercises/sessions as done, messages their instructor, can export or delete their own data. Patients do not manage other patients and cannot see other instructors' or other patients' data.

## 3. Data model

The schema lives in `supabase/migrations/` (numbered SQL files, applied with `node scripts/migrate.mjs` — safe by default since 2026-10-08: no flag only lists pending files; `--baseline <file>` records files as already applied, `--only <file>` applies one, `--apply` applies all pending. Scalingo's `schema_migrations` log is incomplete, so baseline it before any `--apply`). **That directory is the source of truth for the schema — do not hand-copy or re-describe individual columns here, they will drift.** Read the migrations directly when you need exact column names/types.

Conceptually, the schema is organized around:

- **Identity**: `instructors`, `patients` (owned by an instructor), and `app_users` — live today, not Phase-2-only: it's the Clerk-id ↔ internal-uuid mapping every login resolves through (`lib/auth/user-map.ts`), and `current_app_user_id()` (every RLS policy's identity check) reads through it. `auth.users`/`auth_tokens` (migration `0017`) are the actually-unused ones — leftover scaffolding for the abandoned Auth.js replacement-of-Clerk plan (see §7), not touched by any live code path.
- **Exercise library**: `exercises` (shared library, any instructor can use any exercise), `conditions` (named protocols, e.g. "Lombalgie chronique"), `workouts` (session alternatives within a condition), `workout_exercises`, plus `instructor_hidden_exercises` (per-instructor hide list). A workout with `patient_id` set is a **patient-specific copy** created by « Ajuster la séance » (`source_workout_id` points at the original); it is visible only to that patient and their instructor (migration 0044) and never appears in library lists. Each exercise also carries the equipment it strictly needs (`exercises.equipment`, migration 0065, ids and matching rule in `lib/exercise/equipment.ts`): in « Ajuster la séance » the kiné sees the patient's declared equipment, and the list sorts itself from that declaration, with no button: feasible exercises first, the ones the patient lacks equipment for at the very bottom under a « Matériel que X n'a pas » heading, each with an orange pill naming what's required — still selectable, never blocked (Philippe, 2026-10-12). The equipment tagging was done by Claude from names/instructions; the partner kiné's clinical review is done (Philippe, 2026-11-01).
- **Assignment & adherence**: a patient is assigned a `condition` and an ordered list of recommended workouts (`patient_recommended_workouts`, migration 0035); completing a session writes a `workout_logs` row. `patient_profiles` and `patient_feedback` hold richer per-patient clinical/intake detail beyond the Phase-1 basics. `patient_documents` (and message attachments) were deliberately dropped entirely (migration 0056, 2026-09-13) — see §6.
- **Billing** (new model, migration 0071): `instructor_connect_accounts` (Stripe Connect account id — its own table so a kiné can't redirect his patients' payments), `instructors.review_price_cents`, `patient_follow_ups`, `monthly_reviews`, `instructor_platform_billing`, `platform_invoices` — all written only by the server (`internal.*` functions). `subscriptions` and `instructors.tier_*_cents` are leftovers of the old model, kept as history, unused.
- **Messaging**: `patient_messages` — instructor-to-patient messaging, already live (dashboard patient detail page and the patient app both use it).
- **Compliance**: `0018_health_data_consent.sql`, `0019_terms_acceptance.sql` — explicit consent gates, required before a patient can proceed.

### RLS rules to enforce

- An instructor can read/write only rows in `patients` where `instructor_id` matches their own auth id, and can read `workout_logs` of their own patients.
- A patient can read only their own row in `patients`, and can read/write only their own rows in `workout_logs`.
- `exercises`: platform exercises (`created_by` null) and kiné exercises published by Philippe are readable by every signed-in kiné and patient; any other kiné exercise only by its author and his patients — and one reserved to a patient (`patient_id`) only by that patient (migration `0081`, which replaced the old « every signed-in user reads everything » rule that showed one kiné's private exercises to all the others). Only instructors insert/update/delete, only their own; platform ones are read-only; a kiné can never publish himself, and a published exercise is frozen (trigger `exercises_guard_kine_changes`).
- `conditions`, `workouts`, and `workout_exercises` are readable by all authenticated users. Pre-loaded platform rows (`created_by` is null) are read-only to instructors. An instructor can insert their own conditions/workouts and update/delete only their own.
- RLS is enabled on every table from the start — never add a table without RLS policies in the same migration.

## 4. Core user flows (current)

**Instructor**
1. Sign up (`/signup/kine`): **open signup, approved automatically (Philippe, 2026-11-02)** — he pays for access, so his Ordre registration is no longer checked. Form: optional RPPS first (« Retrouver mon cabinet » looks it up in the Annuaire Santé via `lib/instructor/rppsLookup.ts` and offers to pre-fill cabinet name / address / phone in one click; unknown number → he just fills the fields), then cabinet name, address, phone (required), SIRET (optional), then the Clerk account. `app/signup/finalize` creates the instructor row and approves it at once (`setInstructorStatus`); a verified RPPS only adds the « RPPS vérifié » badge. Old accounts left `pending` with a cabinet are approved on their next visit (`app/dashboard/layout.tsx`). Philippe can still suspend a kiné from `/admin`.
2. See a list of their own patients; add a new patient (Clerk invitation, patient sets their own password via Clerk's flow). **Or by QR code (2026-11-04)**: « Ajouter un patient » shows the kiné's personal QR code / link `/rejoindre/<kiné id>.<HMAC signature>` (`lib/patient/joinLink.ts`, `components/JoinQrCard.tsx`); the patient gives name + e-mail, the server creates his `patients` row under that kiné via `internal.join_patient_by_link` (migration `0082_patient_join_link.sql`, applied 2026-11-04: kiné must be approved, e-mail not already a patient/kiné) and sends the same Clerk invitation. Same `PATIENT_INVITATIONS_OPEN` gate (only the admin's QR works before launch).
3. Assign the patient to a **condition**, which already offers several **workouts** (session alternatives). Optionally recommend a specific workout.
4. Create their own conditions/workouts/exercises in addition to the pre-loaded platform library. **Kiné-created exercises (Philippe, 2026-11-04, idea of Jonathan Feltus; migration `0081_kine_exercises.sql`):** « + Créer un exercice » on « Mes exercices » opens a 3-step form (`components/NewExerciseWizard.tsx`): 1) the movement — name with a « cet exercice existe peut-être déjà » search and « Partir de cet exercice » (copies a platform exercise, its Jules video included, `source_exercise_id`), body zones, equipment, numbered steps (stored as sentences, which the guided séance splits back into steps); 2) a video filmed on the phone (`components/KineVideoUpload.tsx`: tips to keep the camera set down and still — Philippe, 2026-11-04 —, mandatory « la personne filmée a donné son accord », never the patient himself: patient videos would be health data and R2 is not HDS); 3) for whom — his bank, or one patient only (`exercises.patient_id`, shown only in that patient's « Ajuster la séance »), plus the encouraged « Rendre public pour tous » box (`publication_status = 'pending'`). He uses the exercise at once; only « public » goes through Philippe in `/admin` → « Exercices des kinés » (`app/admin/KineExercises.tsx`): « À vérifier » (Publier / Demander une modification / Garder privé, with a message the kiné reads in the exercise's sheet) and « À dessiner » (every new exercise, even private, so Philippe can add a blue demo; « Dessin fait » sets `admin_seen_at`). A published exercise is frozen (no edit, no delete) and shows « Proposé par <name · cabinet> » to other kinés. Recognition, sober on purpose (Philippe, 2026-11-04: the first « game » version with trophies and tiers was judged « AI slop »; modelled on GitHub contributors, Figma Community « by », Stack Overflow): other kinés' published exercises carry « Proposé par <initials> <name · cabinet> » in muted text (`components/ContributorCredit.tsx`); under the « Mes exercices » title a quiet line shows an initials stack « Bibliothèque enrichie par N kinés » (→ `/dashboard/exercises/contributeurs`, a plain ranked table: top 10 + the kiné's own row), his « X publiés · Y en vérification » and, from 5 published, an outline badge « Contributeur EasyPhysio » (×10, ×20 at 10 and 20; `contributorTitle`, `components/ContributionSummary.tsx`), also shown under his name in the sidebar. No colours, bars, trophies or celebration. No money involved: the former fee waiver (`instructor_fee_waivers`, migration 0081) is unused; `/admin` neutralises it (`NO_FEE_WAIVER` in `app/admin/exerciseActions.ts`). Videos go straight from the phone to R2 under `exercises/kines/<exercise id>/` with a 15-min presigned PUT (`lib/storage/r2-upload.ts`, needs `R2_UPLOAD_ACCESS_KEY_ID` / `R2_UPLOAD_SECRET_ACCESS_KEY` on Scalingo and a CORS rule allowing PUT from the site on the bucket; the server never receives the file because `proxy.ts` caps request bodies at 10 MB).
5. View a patient's **adherence** (completions vs. recommended times/week), and message the patient directly.
6. From the patient page, click « Ajuster la séance » to add/remove exercises for that patient only — the app copies the séance for them and sends them an automatic message.
7. « Suivi & facturation » (`/dashboard/facturation`): activate his Stripe Connect payments, see his subscribed patients and what he earns (€6.00 per patient per month in which he updates the programme, paid straight to his account, fee note in his name), download fee notes + monthly recap + CSV. EasyPhysio is free for the kiné: no subscription, no price to set (see Billing below). Nothing billing-related on the patient page (Philippe, 2026-10-27: keep pages simple).

**Patient**
1. Arrive through the kiné's QR code / personal link (`/rejoindre/[code]`), log in (Clerk), accept CGU, then **the paywall straight away** (`/patient/suivi`, `PaywallVideo.tsx`: two strips of the steadiest filmed exercises sliding top to bottom + duration slider and price; Philippe, 2026-11-04: « tant que cela n'a pas été débloqué, le patient ne peut pas accéder au reste ») — nothing else opens until he subscribes (10 days free, then one of the three offers, see Billing below), whether or not his kiné has activated Stripe yet. Only then the onboarding wizard (situation, profile, equipment, health-data consent). The two amounts are accepted in writing before the card is saved (`patientMustSubscribe`, `lib/billing/patientPlans.ts`; `/patient/compte` stays reachable for data export/deletion). Order enforced by `app/patient/layout.tsx` + `lib/patient/home-data.ts` (`isProfileComplete`).
2. See workout alternatives for their condition, with the instructor's recommendation highlighted.
3. Open a workout, do the guided session (pain feedback at the end; the phase brake in `lib/exercise/stageProgress.ts` only ever slows progression down), and mark it done → `workout_logs`.
4. Message their instructor; from `/patient/compte`, export their data (JSON) or delete their account.

**Billing (money flow) — DEFINITIVE MODEL OF 2026-11-04 (Philippe: « LETS KEEP THIS VERSION AS DEFINITE »). Replaces every earlier model; all amounts live in `lib/billing/patientPlans.ts` only, never hard-coded.** The kiné uses EasyPhysio for free. The patient pays, per month, **two distinct services sold by two distinct sellers, charged as two distinct payments on the same card, with two distinct invoices**. Three offers on the paywall (Philippe, 2026-11-04, relayed and approved: « ok yh fair »; « put 12.99 and underneath we explain exactly the origin of the sum »): no commitment €6.99 + €6 = €12.99, 3-month commitment €3.99 + €6 = €9.99, 6-month commitment €2.99 + €6 = €8.99 per month at most (`PLATFORM_OFFERS`, keys `plan_1m` / `plan_3m` / `plan_6m` on EasyPhysio's account — the same keys on a KINÉ's account are the old model). The commitment binds only the platform part, counts from the first paid month, is stored in the Stripe subscription metadata `commit_until`; cancelling during it sets `cancel_at` = its end; after it, the access continues at the same price month to month, cancellable any time:
1. **Platform access — €6.99 / €3.99 / €2.99 incl. VAT per month depending on the commitment, sold by EasyPhysio** (net after VAT and card fees ≈ €5.48 / €3.02 / €2.20): a Stripe subscription on EasyPhysio's OWN account (Checkout `mode: subscription`, 20 % VAT tax rate « inclusive », created once by `platformVatRateId`), **10-day free trial on the first subscription only** (`TRIAL_DAYS`), billed **every month of access whether or not the kiné does anything** — it is the price of the app (hosting, videos, messaging), never a share of the kiné's act. Recorded in `subscriptions` with `plan` = the offer key (`patient_monthly` = the €3.99 no-commitment access sold briefly on 2026-11-04, still recognised; all keys already allowed by migration 0080, no DB change) and `stripe_account_id = null` (= EasyPhysio's account), HMAC-signed metadata with the account key `"platform"` (`lib/billing/subscriptionSignature.ts`), synced from the webhook (events without `event.account`), the payment return `app/patient/suivi/retour` and a re-read when the period has passed (`lib/billing/patientSubscription.ts`).
2. **The kiné's programme — €6.00 / month, sold by the kiné** (≈ €5.66 net after card fees): at subscription, the card saved on EasyPhysio's account is **cloned onto the kiné's Connect account** (`ensureKineCard`, Stripe « cloning » of a PaymentMethod + a customer on the kiné's account, stored in `patient_follow_ups`); the first time in a calendar month the kiné assigns / adjusts / saves the patient's séance (`lib/billing/autoReview.ts`, called from `app/dashboard/patients/[id]/actions.ts` and `app/dashboard/seances/actions.ts`), a `monthly_reviews` row is recorded with its sequential fee-note number and an off-session PaymentIntent of €6.00 is made **directly on the kiné's account, with NO application fee** (`lib/billing/followUp.ts`). Only if the access subscription is `active` and not `trialing` (`kineFollowUpChargeable`), the kiné is not suspended and his Connect is active. Never during the trial, never before the act.
**Why two payments (legal audit 2026-11-04, `reports/Frais plateforme patient kiné légalité.md`): EasyPhysio never takes money out of the kiné's payment** (no `application_fee` / `application_fee_percent` anywhere) — otherwise the €3.99 would be a share of his fees (art. L.4113-5 via L.4321-19, R.4321-72 CSP). Verdict of the audit for this setup: 🟠 defensible, not validated; residual risks listed in `docs/messages-validation-juridique.md` (mandatory patient fee vs. the 2024 teleconsultation decree / Oct. 2026 bill, R.4321-98 « par correspondance » / télésoin, imposed payment method). Access rules: active or trialing → access, even cancelled until the end of the month; refused card → locked at once; cancelling stops both payments. Patients get in without paying only when the kiné is suspended, or for admin test patients with « accès gratuit » (`patients.trial_ends_at`). A kiné who has not activated Stripe yet no longer exempts his patients (2026-11-04): they subscribe to the access as usual, and the card is copied to the kiné's account at his first programme update once his Connect is active (`lib/billing/autoReview.ts` → `ensureKineCard`). Deleting a patient and suspending a kiné cancel the access subscription at Stripe immediately (`lib/billing/suspendInstructor.ts`). **Previous models are off**: the 1/3/6-month plans of 2026-11-02 (`plan_1m/3m/6m` on the kiné's account with `application_fee_percent`) are no longer sold; any still running keeps access until the end of its paid period and is set to `cancel_at_period_end` the first time it is seen; the kiné subscription of 2026-11-01 stays switched off (`KINE_SUBSCRIPTION_BILLING = false`); `instructors.review_price_cents` is not read. Home page « Et moi, comment je suis payé ? » (`components/KinePlans.tsx`), FAQ, CGU (`app/cgu/page.tsx` + `legal/cgu.md`) all show this model. **Stripe dashboard setup still to do by Philippe**: platform webhook endpoint with checkout.session.completed, customer.subscription.created/updated/deleted, invoice.paid/payment_failed; Connect endpoint with payment_intent.succeeded/processing/payment_failed and account.updated; customer e-mails (receipts/invoices) on, with EasyPhysio's legal details on invoices; Stripe Billing fees (≈ 0.7 % of subscription volume) apply to the access subscription. ## 7. Active migration: Supabase → Scalingo (HDS compliance)

**This is now the standing target architecture, not a someday-maybe** — real French patient health data legally requires HDS-certified hosting (art. L.1111-8 CSP), and Supabase/Vercel are not HDS-certified. Scalingo is, and this migration is how the app gets there. As of 2026-09-13 the mechanics are fully proven and the app's data-access code is already rewired for it — what's left is operational (see below), not more architecture work. Do not propose the old "Auth.js/NextAuth replaces Clerk" plan described in earlier drafts of this file — that was abandoned; **Clerk is kept** (HDS certification covers hosting of health data, and Clerk never holds health data, only identity).

**The architecture**: the app's own code is unchanged from a Supabase-shaped mental model — it still calls `@supabase/supabase-js`, still enforces per-instructor/per-patient isolation via Postgres RLS policies keyed on `current_app_user_id()`. What changes is only what's *behind* that client:
- **PostgREST** (self-hosted on a Scalingo app, `easyphysio-postgrest`) replaces Supabase's own REST layer. It verifies the same Clerk session JWT the app already sends (via Clerk's public JWKS), and RLS policies apply exactly as before.
- A tiny **Caddy** reverse proxy sits in front of PostgREST in the same container, because `@supabase/supabase-js` hardcodes calling `<url>/rest/v1/<table>` — PostgREST itself serves tables at the root, so Caddy strips the `/rest/v1` prefix before forwarding.
- Scalingo's managed Postgres role has neither `CREATEROLE` nor `BYPASSRLS` (verified directly against the database) — there is no way to recreate Supabase's `service_role` bypass-everything key. The ~19 places that used to call `createAdminClient()` now do one of two things instead: (a) go through the *normal* RLS-scoped client, where a real policy already (or newly) allows it, or (b) call one of a small number of narrow, single-purpose SQL functions living in an `internal` schema that PostgREST never exposes (`lib/db/admin.ts`, a direct, server-only Postgres connection — see `supabase/migrations/0057_scalingo_admin_bypass_functions.sql` for the full design rationale and a real security lesson learned building it: `revoke execute from public` does nothing when there's only one Postgres role, since the role owns every function it creates).
- These same functions/policies are also applied to the still-live Supabase database, purely additively, so the exact same application code works correctly on both backends during the migration window — see that migration file's own notes.

**What's actually left (operational, not architectural)** — see the memory note "HDS hosting requirement" for the full step-by-step cutover runbook: refresh the Scalingo data copy one final time, flip `NEXT_PUBLIC_SUPABASE_URL` and `SCALINGO_DATABASE_URL` to the real (non-test) values, a full manual smoke test, then promote the test PostgREST app to permanent infrastructure. Philippe has not yet bought a production domain name or moved Clerk to a production instance — neither is required to finish the Scalingo cutover itself (Scalingo provides a free `*.scalingo.io` subdomain, same idea as Vercel's `*.vercel.app`); both only matter for the actual public launch, which is also still waiting on the exercise demonstration videos being filmed and added to the platform.

**Two-stage plan, decided 2026-09-13**: development moves onto Scalingo starting now — today's `easyphysio` app runs in Scalingo's `osc-fr1` region, which is **not** HDS-certified (only `osc-secnum-fr1` is, and that region needs a Scalingo support request to unlock). That's fine for now since there is no real patient data yet (pre-launch). The plan is explicitly two stages, not one: (1) now — finish the cutover onto Scalingo's ordinary region, as the new standing development target; (2) at actual public-launch time, once the exercise videos are filmed and on the platform — upgrade the Scalingo subscription to the HDS-certified `osc-secnum-fr1` region/plan, *and* handle the other launch-gated items together (buy the domain, move Clerk to production, legal review). Don't treat stage 1 as if it were already HDS-compliant — it isn't yet, on purpose, until stage 2.

**AI-generated rehab protocols** (`lib/ai/protocol.ts`, `app/api/protocol/route.ts`). Currently a mock/placeholder with invented example conditions and exercises, not wired to any UI. This is meant to become a real feature eventually, but only once it's built on the clinical partner's real protocols — never on invented/mock clinical content, and never connected to real patients before that clinical review happens. The current placeholder data must not be mistaken for reviewed clinical content. (This one really is someday-maybe, unlike the Scalingo migration above — don't build on it unprompted.)
