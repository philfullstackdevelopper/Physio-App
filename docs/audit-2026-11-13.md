# EasyPhysio audit — 13 November 2026 (after the HDS switch)

Read-only audit: no code changed, no data changed. Code audited: `main`, commit `c6ce8cf` (the version live on easyphysio.fr). It follows the audit of 10 November (`docs/audit-complet-2026-11.md`) and checks which of its points are really fixed.

**How it was done.** Five parallel code reviews (login/signup, database rules, payments, server actions, site/infra/legal), tests of the live site from outside without logging in, and read-only queries on the live database. "Confirmed" = I checked it myself on the live site or live database. "Read in code" = established by reading the code, not tried for real. "Suspected" = depends on something I can't see (Stripe, Clerk, Scalingo settings).

**Not covered:** screens after login on the live site (no session), the Stripe / Clerk / PostHog / R2 dashboards, the mobile app in depth.

## 1. Fix first (exploitable today, because kiné signup is open and auto-approved)

### U1 — Any new kiné can open patient sign-ups before launch (High, confirmed in code and live database)
- **What.** The site decides "is this the admin's QR code?" from the e-mail stored on the kiné's own row (`instructors.email`). A kiné can change that field himself: the live rule `instructors_update_own` lets him edit his whole row, and no trigger locks the e-mail (live triggers on `instructors`: status, RPPS, block sync, private exercises — nothing for e-mail).
- **Where.** `app/rejoindre/[code]/actions.ts:60`, `page.tsx:64`, `lib/launch.ts:11`, `supabase/migrations/0082_patient_join_link.sql:40-53`, `0031:70-74`.
- **Scenario.** Someone signs up as kiné, sets his row's e-mail to your admin address by talking to the database directly, then uses his own QR link: the form is open, patient records are created and EasyPhysio invitations go out to any address (20 a day). Real patients could enter before you open, and anyone can receive e-mails in your name.
- **Fix.** Decide from the identity the server holds (the account's own e-mail or an admin id list), and lock `instructors.email` with a trigger, as was done for patients.

### U2 — The migration log is open to the whole internet (Medium/High, confirmed live)
- **What.** `public.schema_migrations` is the only table without protection. Without logging in, anyone can read it and — confirmed with requests that matched no rows — modify or delete rows.
- **Scenario.** Someone empties it: the next `migrate.mjs --apply` replays all 89 files, including the ones that delete exercises. Or someone adds a fake line so a future security fix is silently skipped.
- **Fix.** Move the table to the `internal` schema (not exposed) and update `scripts/migrate.mjs`.

### U3 — A kiné can delete a patient directly, and the patient keeps being charged (Medium, confirmed live rule)
- **What.** The live rule `patients_delete_by_instructor` lets a kiné delete his patient by talking to the database, skipping the site's steps (stop the Stripe subscription first, remove the login).
- **Scenario.** The record, health profile and messages disappear; the 6.99 € subscription keeps being charged to someone who no longer has an account; re-inviting him is then refused.
- **Fix.** Remove that rule; delete only through a server function that does the cleanup.

### U4 — A race can delete a patient who was just created (Medium, read in code)
- **Where.** `app/rejoindre/[code]/actions.ts:75-101`, `app/dashboard/patients/actions.ts:66-94`.
- **Scenario.** Two submissions for the same e-mail at the same moment (double click, or two kinés): the second creates the patient and sends the invitation, the first then "cleans up" and deletes that patient. He holds a valid invitation and lands on "account not linked".
- **Fix.** Delete a reservation only if nobody logged in with it and no patient record uses it.

### U5 — No DMARC on easyphysio.fr and easy-physio.fr (Medium, confirmed)
- Anyone can send e-mail that appears to come from your address. One TXT record at OVH (`_dmarc`, start with `p=quarantine`). SPF exists (`~all` on the main domain; `-all` would be stricter).

## 3. Accounts, login, identity

- **RPPS "verified" badge** is still obtainable with any kiné's public name and number (`lib/instructor/rppsVerification.ts:53-81`). With auto-approval, a fake kiné gets a trusted badge.
- **Admin recognised by e-mail only** (`lib/admin.ts`), without checking that Clerk verified it. Protected in practice today; pin your Clerk id as well.
- **E-mail change → possible account takeover (suspected).** The site never updates its copy of a user's e-mail; if a user changes e-mail in Clerk, whoever later verifies the old address gets the old account.
- **Suspension is bypassed by signing up again** with another e-mail (consequence of auto-approval).
- **The QR link reveals whether an e-mail is already a patient or kiné** ("emailTaken"), never expires and can't be revoked. Dormant while invitations are closed — but see U1.
- **Rate limits are weak:** kept in memory per container (two containers since today = double), and keyed on a header the visitor may be able to forge (suspected, depends on Scalingo). The waiting list has only a global cap of 200/hour that one robot can exhaust.
- **`SIGNUPS_OPEN` is enforced on pages only**; harmless while it is `true`.
- **Two security promises depend on settings I can't see:** e-mail verification mandatory in Clerk; development Clerk keys still trusted by the production database (remove at launch).

**Checked and correct:** every admin and dashboard action re-checks the role on the server; roles live in the database only; a kiné can't approve himself, lift a suspension or give himself the badge; QR codes can't be forged; no open redirect; a database outage during login creates or deletes nothing; the fixes for "kiné deletes another kiné" and "free access for life" are installed on the live database.

## 4. Data isolation and server code

- **All 63 filmed videos can be fetched without an account** (`lib/storage/video-actions.ts:53-58`): a 6-hour link for any filmed exercise, no login, no limit. Deliberate for the demo, but a competitor or unpaid patient can take the whole catalogue. Your decision: restrict to a few demo videos.
- **A kiné can put any address in an exercise's video field** (`set_exercise_media`): an external link that tracks patients and you in `/admin`, or another file in the bucket; he can also swap the video between your review and "Publish".
- **Pathologies are shared between all kinés and deletable by their author:** kiné A deletes a pathology he created; kiné B's unused sessions built on it are deleted and B's patients lose their pathology. A suspended kiné can still do it.
- **Two actions can destroy data after a failed read:** `deleteSeance` (patients lose their assigned session) and "Ajuster la séance" (a patient's session can be emptied) — `app/dashboard/seances/actions.ts:260-268`, `app/dashboard/patients/[id]/actions.ts:369`.
- **Session writes from the patient's browser go straight to the database** without the payment/consent check (the pages and server actions do check).
- **Smaller:** a patient sees his kiné's whole record (SIRET, phone); no length limit on messages and several text fields; a patient name starting with `=` lands as a formula in the kiné's CSV export; a kiné can reset his own daily QR quota; unbounded reads on the dashboard (will slow down over time).
- **Deletion leaves data behind (still open):** Stripe customers (name, e-mail, card copy) are never deleted; videos are never removed from R2; no procedure to delete a kiné account; the data export misses a few items.

**Checked and correct:** private tables return nothing without login (tested live on 19 tables); every table except the migration log has forced protection (live); isolation between kinés holds on patients, profiles, logs, messages, fee notes, cabinets; no SQL injection; kiné video upload is confined to his own exercise; cron route closed without its secret; old database gateway no longer answers.

- English site invisible to search engines (same address, no `hreflang`).
- `npm audit`: 0 critical; 1 high and 7 moderate in development tools only (not shipped). Next.js is on the fixed version 16.4.6.

**Fixed since 10 Nov (checked live):** security headers present; error pages; page titles; canonical address and "noindex" on the Scalingo host; HTTPS forced, old TLS refused.
